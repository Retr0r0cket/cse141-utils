# Testing

There are five layers of tests. The test programs (course, custom, stress) run on the whole
system; the AHB-Lite suite runs them again with wait states, under a bus protocol checker; random
programs are compared against a golden model; unit testbenches check single parts exhaustively
or against a model; and `just test-all` runs everything with one summary.

The golden model is the backbone. Every expected output we make ourselves comes from
`tools/thumb_iss.py`, written from the ARM architecture's rules rather than from our RTL, so a
test built on it doesn't share the core's mistakes. The model is itself checked against every
course program with expected files.

## `just test-all`

`tools/test_all.sh [--quick] [--fuzz N] [--netlist-fuzz N] [--seed S]` runs these steps. Each
step's output goes to `build/test-all/<step>.log`, and the summary lists PASS or FAIL for each.
It exits 1 if anything fails.

| # | Step | What it checks |
|---|---|---|
| 1 | lint | `just lint cpu_core` (Verilator `-Wall`) |
| 2 | golden model | `tools/check_iss.py`: the ISS agrees with every course program's `.pcs`, `.after.dmem` and `.bus` |
| 3 | stress up to date | `tools/gen_stress.py --check`: `test_programs/stress/` is exactly what the generator makes |
| 4 | unit tests | `alu_tb`, `fetch_tb`, `decode_tb`, `peripherals_tb` (below); each prints `PASSED` |
| 5 | test programs (RTL) | `just test-programs`: every program passes, and the public total is within budget |
| 6 | reset and rerun | `just test-program-restart` on every program: run, reset, run again, same outputs |
| 7 | AHB-Lite, with waits (RTL) | `tools/ahb_suite.sh --waits '0 50' --seeds 1` (below) |
| 8 | random programs (RTL) | `tools/fuzz_cores.py --ref iss`, 500 programs by default |
| 9 | netlist | `just synthesize-mac` then `test-programs-synth-mac`: every program on the synthesized core |
| 10 | AHB-Lite, with waits (netlist) | step 7 on the synthesized core (`--netlist`) |
| 11 | random programs (netlist) | the same fuzzing on the netlist's simulator (`--dut-exe`), 200 by default |

`--quick` skips steps 9 to 11 (synthesis takes a while). The week 6 grading needs every test to
pass in RTL **and** on the netlist, so run the full suite before submitting.

## Test programs (`test_programs/`)

Each program is a folder `NN_name/` holding `name.imem` and its expected files. `just
check-program` compares:

- `.pcs`: every instruction that reaches execute, in order (repeats merged).
- `.after.dmem`: SRAM at the halt.
- `.bus`: stores, and device loads, in order. Normal loads and fetches are ignored.
- `.mem_sizes` (optional): `CODE_SIZE=N`, `SRAM_SIZE=N`.

| Folder | Where it comes from | What it's for |
|---|---|---|
| `level0`–`level5` | the course (public) | the graded programs; their cycles count toward the budget and the score |
| `c` | the course | compiled C programs (peripherals, the counter) |
| `custom` | ours | prefetch stress, loads during fetch's start-up, running off the end of Code, BL backwards, ADD PC onto a B, branch corner cases, a saved random program |
| `stress` | `tools/gen_stress.py` | directed programs for every datapath (below) |
| `submit` | ours | the LED programs to submit (`ledTimer`; `ledExact`, generated by `tools/gen_led_exact.py`) |

### Stress programs (`tools/gen_stress.py`)

There are 36 programs, built with `tools/thumb_asm.py`, with expected outputs from the golden
model. Every program saves each result, and the flags, to SRAM. The flags are captured with
branches over flag-neutral moves, so `.after.dmem` checks all of them.

| Programs | What they cover |
|---|---|
| `aluAdds` … `aluCmn` | ADDS, SUBS, ADCS, SBCS, CMP, CMN on every pair of edge values: result and NZCV |
| `aluImm` | ADDS/SUBS `#imm3` and `#imm8`, CMP and MOVS `#imm8`, RSBS, on edge values |
| `logicAnds` … `logicTst` | ANDS, ORRS, EORS, BICS, MVNS, TST: N and Z set, C and V kept (from both starting states) |
| `shiftLsls` … `shiftRors` | Register shifts at every amount edge (0, 32, past 32, Rm past 255), C kept or set |
| `shiftLslsImm` … `shiftAsrsImm` | Immediate shifts by every amount (LSLS `#0` is MOVS; LSRS/ASRS `#0` mean 32) |
| `extend` | SXTH, SXTB, UXTH, UXTB, REV, REV16, REVSH on edge and sign-boundary values |
| `memory` | Every store and load size, every alignment, register and immediate offsets: byte lanes in and out, sign extension |
| `literal` | ADR and LDR literal from either half of a word (PC reads as `Align(PC + 4, 4)`) |
| `forwardAlu`, `forwardLoad` | Each ALU or load result used 1–4 instructions later as A, B, store data, shift amount, shift data, address offset, compare, MOV. For loads the destination is poisoned first, so a stale value can't pass. |
| `branches` | All 14 conditions against 8 flag states, taken and not, forward, and backward loops |
| `calls` | BL forwards and back from both halves of a word, returns by BX LR and MOV PC, ADD PC jump tables, BX to computed (and upper-half) addresses |
| `peripherals` | LED writes and reads (with their APB wait) used right away; the counter's CLEAR |
| `fetch` | 16 stores then 16 loads back to back (fetch starved of the bus), then BLs from both halves of words |
| `haltAfterStore`, `haltAfterDeviceLoad`, `haltAfterBranch`, `haltInCall` | A halt right after a store, after a device load, at a branch target (halts on the wrong path), inside a call |
| `busBackToBack` | Loads and stores with nothing between: stores of different data back to back (a waited store's data must hold while the next one's address waits), sizes mixed on one word, store then load, LEDs and SRAM interleaved, stores right after taken branches |
| `leds` | All 64 LED values with junk above bit 5 (which reads back as 0); writes and reads at other offsets in the LEDs' 4 KB (it's all one register); a read used right away as an address offset and in a compare |
| `counter` | The cycle counter: CLEAR then COUNT, two reads back to back, a 100-iteration loop, writes to COUNT and to empty offsets ignored, CLEAR and empty offsets read 0, a CLEAR written with a nonzero value |

The `counter` program reads COUNT, whose value depends on timing. It checks each value against a
range in the program (at least 200 after a 200-instruction loop, for example), runs a trap if
it's out of range, and stores only a marker. So its outputs are the same for any core, and for
any wait states. The golden model gives COUNT a stand-in value (two cycles per instruction since
the last CLEAR) for these programs only. Everywhere else, a read of COUNT is still an error.

A failed check jumps to a `UDF #1`. The core doesn't halt on that, and the ISS refuses it, so a
generator bug shows up as an error.

The generator writes files in place and only rewrites changed ones. Deleting and remaking the
folder made iCloud's Desktop & Documents sync leave empty `NN_name 2` copies behind, which then
"failed".

## The AHB-Lite suite (`just ahb-suite`)

`tools/ahb_suite.sh [--waits "0 25 50 75"] [--seeds N] [--groups "..."] [--jobs N] [--netlist]`
runs every test program on `testbench/ahb_lite_tb.sv`, with these settings:

- once with no waits,
- then `--seeds` times (2 by default) at each nonzero wait percentage.

`ahb_lite_tb` holds `program_tb` unchanged, so it writes the usual output files, and
`check-program` checks them. Around it, a protocol checker watches the core's manager port every
cycle. The waits come from `ahb_mem`'s `+MEM_WAITS=<percent>`: each data phase cycle in memory
waits with that chance, so data phases of one cycle to many come up, along with held address
phases and held store data. A run passes when:

- the checker finds no violation,
- `.pcs`, `.after.dmem` and `.bus` are right.

`.led_on` is a cycle count, so it's only checked without waits. Each run's line shows what it
saw (transfers, waited cycles, held address phases, held store data), so a run that never waited
is easy to spot. `--netlist` runs the synthesized core from `build/synth-fpga/`.

The checker's rules, from AMBA AHB (IHI 0033C) and the course's notes:

| Rule | Checked |
|---|---|
| Reset | `htrans` is IDLE while `reset_n` is low |
| No X | `htrans` never; an address phase's `haddr`, `hwrite`, `hsize`, `hburst`, `hprot`, `hmastlock` never; a store's `hwdata` never in its byte lanes |
| Singles only | `htrans` IDLE or NONSEQ, `hburst` SINGLE, `hmastlock` 0 |
| Size and alignment | `hsize` at most a word; `haddr` aligned to it |
| `hprot` | `0010` for a fetch (always a word read), `0011` for a load or store |
| Waited address phase | NONSEQ with `hready` low: every address and control signal is the same next cycle |
| Waited store data | `hwdata` holds through the whole data phase, in its byte lanes |
| Where it goes | Code, SRAM or the peripherals only (never ERROR); no write to Code; words only to the peripherals; `hresp` never ERROR |
| Halt | In `halt_o`'s cycle, no load or store starts, and none is still waiting |

The checker doesn't require the address signals to hold while `htrans` is IDLE in a wait.
AHB-Lite lets a manager drive IDLE there, then NONSEQ once `hready` is high.

The full default suite runs 553 runs in about 2 minutes, and passes on the RTL. `--waits "0 50"
--seeds 1` (158 runs) also passes on the netlist.

## Random programs (`tools/fuzz_cores.py`)

These are differential tests. Each random program always halts. It contains:

- forward branches anywhere,
- backward branches only as counted loops,
- BL calls returning through BX LR,
- loads and stores to a block of SRAM,
- NOPs that put branch targets and BLs in either halfword.

A halt follows every unconditional branch and fills every skipped stretch, so running anything off
the right path ends the program early. At the end, every register is stored, so SRAM holds the
whole machine state.

The program runs on the reference and the DUT, which must agree on the PC trace and the final
SRAM:

- `--ref iss`: compare against the golden model.
- `--ref <repo>`: compare against another core.
- `--dut-exe <sim>`: use an already-built simulator, for example the netlist's
  `build/synth-fpga/program_tb_synth`.

`--count`, `--seed` and `--runs` (resets between runs) control a campaign. Failing programs are
kept under `--keep`.

## Unit testbenches (`testbench/`)

Run one with `just test <name>`.

| Testbench | Unit | How |
|---|---|---|
| `alu_tb` | `arithmetic_logic_unit` + `shift_factor_generator` | Compared against a model written from ARM's `AddWithCarry` and `Shift_C`, for every function: every pair of edge values, 2000 random pairs, both carries, and every shift amount 0–255 (and a high byte that must be ignored). About 103k checks. |
| `fetch_tb` | `fetch_stage` + `instruction_buffer` | Depths 4, 8, 16, 32 and reset addresses 0, `0x102`, `0x1FFE`, all at once. Random grants, bus waits (read data is X while waiting), decode stalls, redirects (including upper halfwords and the top of Code) and resets. Every instruction decode gets must have the right PC, bits, PC + 4, controls, immediate and target. Then a clear stretch that must deliver one instruction per cycle. |
| `decode_tb` | the decoders, `branch_link_decoder`, `decode_stage` | All 65,536 halfwords against a reference decode written from ARM's encoding tables: reads, writes, ALU, flags, memory, branches, immediates, B targets; out-of-scope encodings must do nothing. Then 200k BLs against the ARM offset formula, including the extremes. Then a 300k-cycle scoreboard of ID/EX: every operand, store data, BX/MOV PC/ADD PC/BL targets, BL pairing, flush, hold, stalls and forwarding selects. |
| `peripherals_tb` | the system behind the core: `ahb_interconnect`, `ahb_mem`, `ahb_to_apb`, `led_apb`, `cycle_counter` | A random AHB-Lite manager, in the core's place, sends transfers back to back or with IDLEs between, and resets come at random, mid-transfer too. Each is checked against a model, cycle-exact. SRAM: every size and alignment, junk in the unwritten lanes. LEDs: any offset in their 4 KB, and the `leds` output every cycle. COUNT: exactly the cycles since reset or the last CLEAR. Empty counter offsets: read 0, writes ignored. Unmapped addresses: the two-cycle ERROR. Data phase lengths: APB 2, memory 1. APB: setup then access, with the same `paddr`/`pwrite`/`pwdata`; one `psel` at a time. 200k cycles by default (`+CYCLES`, `+SEED`, `+MEM_WAITS`). |
| `program_tb` | the whole system | the course's test-program bench |
| `manager_tb`, `counter_apb_tb` | the bus and the counter | the course's |

## The extra-credit LED program on other cores

`ledExact` is graded on every correct group's core, so it's tested on cores other than ours
(see `tools/gen_led_exact.py` and [tools.md](tools.md) for how it works). Each core gets its own
`program_tb` build, and the run passes when the first write turning LED 5 on has `COUNT=1000` in
`ledExact.leds`, within the default 10,000 cycles:

- The cores on our branches (`main`, `optimizations`, `redesign` to `area-buffer`,
  `branch-predict`, `btb`, `fast-redirect`, and `origin/ahb`), each checked out as a git worktree.
- Slowed copies of our core that pass the stress programs:
  - decode holding each instruction 1–3 extra cycles,
  - fetch waiting 1–6 cycles after each fetch (CPI 1.6 to 3.8).

All hit 1000 except two of the fetch-starved copies, one fetch every 3 cycles (CPI about 2.0) and
one every 7 (CPI about 3.8), which run out of cycles while searching. The copies fetching every
2, 4 and 5 cycles pass.

## Checking the checkers

Each new test was checked by planting bugs in the RTL and confirming the tests catch them:

- 15 single-line bugs in the core, caught by the stress programs,
- 10 more against the stress set,
- 15 in fetch and decode, of which the testbenches caught 13. The other two had no effect: dead
  logic (see below).

The bus suites were checked the same way:

- `ahb_lite_tb` caught a store's `hwdata` taken in during a wait (once `busBackToBack` was
  there: no earlier program had two stores in a row), a load's address replaced by fetch's in a
  wait, and `hprot` saying "data" for fetches. `htrans` dropping to IDLE in a wait wasn't flagged:
  that's allowed (above), and the programs still pass.
- `peripherals_tb` caught, in our counter, CLEAR decoded from 4 address bits, COUNT at every
  offset, and a reset to 1. In the course's bridge and LEDs (changed for the test only), it
  caught `penable` in the setup cycle, `paddr` changing between setup and access, and the wrong
  LED bits. Two counter changes had no effect seen from the bus: CLEAR in the setup cycle as well
  (COUNT ends at 0 either way), and COUNT on `prdata` during writes (nobody reads it).

The two dead pieces of logic:

- the `+ pop` when the buffer is empty, in `instruction_buffer`'s `head_pc` update,
- the `!redirect` in fetch's `take`, because the clear and the flush already win.

## Running pieces by hand

```sh
just test-programs                      # every program, RTL
just test-program stress/22_memory      # one program
just test-program-restart level3/03_reverse
just test alu_tb                        # a unit testbench
just test peripherals_tb +CYCLES=1000000 +SEED=3
just ahb-suite --groups stress --waits "0 75" --seeds 4
just ahb-suite --netlist                # after just test-programs-synth-mac
python3 tools/fuzz_cores.py --ref iss --count 1000 --seed 7
just test-all --quick
```
